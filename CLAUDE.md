## Commands

Node 24 is pinned in `.nvmrc`. Run `nvm use` first.

- `npm run start:dev`: run the API with auto-reload
- `npm run build`: compile TypeScript into `dist/`
- `npm run lint`: lint with oxlint
- `npm run format`: format with Prettier
- `npm test`: unit tests (Vitest, `src/**/*.spec.ts`)
- `npm run test:e2e`: end-to-end tests (`test/*.e2e-spec.ts`)
- Run a single test file: `npx vitest run src/app.controller.spec.ts`
- `docker compose up -d`: start Postgres (localhost:5432) and Redis (localhost:6380). Needs OrbStack running.
- `docker compose ps`: check both services are `healthy`
- `docker compose down`: stop them (data kept). `docker compose down -v` also wipes the database.
- `npm run db:migrate`: after a schema change, create a migration and apply it to the local database
- `npm run db:generate`: then rebuild the typed Prisma client (Prisma 7 doesn't do this as part of `migrate`)
- `npm run db:studio`: browse the local database in your browser
- The app and the e2e tests need Postgres running (`docker compose up -d`). The app checks the connection at startup.
- Copy `.env.example` to `.env` before running the app.

## What this is

This is the backend for an FPL (Fantasy Premier League) companion. It produces projections and explained recommendations (captain, transfers, team rating), and runs wagers between users using free credits. In v1 it only reads from FPL and never writes to it.

## Planned stack

- TypeScript and NestJS: one codebase with two entry points, `src/main.ts` (the API) and `src/worker.ts` (scheduled jobs).
- Postgres with Prisma (migrations live in this repo), and Redis with BullMQ for jobs and caching.
- The Anthropic API with structured outputs, validated with Zod.
- Vitest for unit tests, and Testcontainers for Postgres integration tests.
- Docker Compose runs Postgres and Redis locally. A seed script loads a saved FPL snapshot, so local development never calls FPL.
- The API deploys to Railway as Docker images in GHCR.

## Architecture

The app is a modular monolith. Modules live in `src/modules/`: `fpl`, `projections`, `wagers`, `social` and `auth`. Keep the boundaries clean so a module can be split out into its own service later.

- **The API never calls FPL or the AI per request.** The worker fills Postgres and Redis on a schedule, and the API serves only from that data. This is how the app survives the 10x traffic spike in the hour before a deadline. When FPL is down, the API serves the last synced data along with its timestamp.
- **Only the `fpl` module talks to FPL**, because FPL's endpoints are undocumented and can change. Raw responses are stored in `gameweek_snapshots` before they are normalised into tables.
- **`src/projections` holds the expected points model as pure functions with no I/O.** It returns ranges (`low` and `high`), not single numbers, and is versioned with `model_version`.
- **AI explanations are generated by the worker and cached per gameweek.** The model only receives structured inputs, never free recall. Validate every output with Zod and fall back to a template sentence if validation fails.
- **Table ownership:** the worker writes the FPL tables, the API writes the user tables, and only the `wagers` module writes `wagers`, `wager_participants`, `ledger_entries` and `settlements`.

## Credits and wager invariants

Breaking any of these is a correctness bug:

- `ledger_entries` is append-only. A balance is always `SUM(amount)`. Never add or update a balance column (a cache is allowed).
- Stakes are deducted when a wager is created and when it is accepted, so nothing is ever owed. Unaccepted wagers refund at the deadline. A tie refunds both sides.
- Settlement runs only in the worker and has no public endpoint. It runs only after `gameweeks.data_checked` is true. Each settlement runs in one transaction, and it is idempotent thanks to the unique `settlements.wager_id`. It reads from the stored snapshot.
- Create and accept endpoints require an `Idempotency-Key` header.
- One verified FPL ID per account, and the same ID can never be on both sides of a wager.
- Stake limits: up to 25% of the balance for private wagers and up to 10% for public ones.
- Credits have no cash value: never add any path to buy or cash out credits.
- Never accept or store FPL passwords on the server. FPL ID ownership is verified with a one-time code placed in the FPL team name.

## API contract

NestJS generates `openapi.json`, and it must be committed whenever the API changes. CI checks that it matches the code. `fm-client` generates its typed client from this file, so an API change that isn't reflected in the spec breaks the client build.

Big decisions get a short ADR in `docs/adr/`.
